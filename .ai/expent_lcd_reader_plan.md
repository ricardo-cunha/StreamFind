# Expanded LCD Reader Implementation Plan

## Working Rules

- Use `devtools::load_all()` for compile and local validation.
- Do not edit autogenerated `RcppExports.cpp` or `R/RcppExports.R` manually.
- Run `devtools::document()` only when exported R/Rcpp signatures or documentation require regeneration.
- Do not add vendor/private LCD fixtures under `tests/testthat/`. Use `dev/dev_reader/` scripts and `dev/dev_reader/example_files/` fixtures.
- Do not create anonymous namespaces in `.h` or `.cpp`; keep the named namespace convention used in the current `reader.cpp` and `reader.h`.
- Do not add legacy DuckDB/cache compatibility code. This phase targets the current schema only.
- Prefer the smallest working native LCD implementation before adding external dependencies.

## Objective

Implement native reading of Shimadzu `.lcd` chromatogram data through the existing `mass_spec::reader` backend.

Current state:

- `.lcd` files are detected by OLE Compound File signature.
- `create_reader()` currently fails with the explicit unsupported-native-decoding message.
- TXT support already reads Shimadzu `[LC Chromatogram(...)]`, `[LC Status Trace(...)]`, and `[MS Chromatogram]` blocks.
- Project/R storage already supports chromatogram-only analyses and extended chromatogram metadata.

Primary target:

- Decode all LC detector/status chromatogram-like streams from `260115_ADC.lcd`.
- Dynamically discover streams; do not hard-code channel names or stream names.
- Validate against `260115_ADC.txt`, which currently imports 8 chromatograms:
  - `Detector A-Ch1`
  - `AD1`
  - `Pump A Pressure`
  - `Pump B Pressure`
  - `Oven Temp.`
  - `Room Temp.`
  - `Sample Cooler Temp.`
  - `UV Cell Temp.`

Secondary target:

- Inspect `karl.lcd` and determine whether its LC/MS chromatogram streams use the same binary layout or require a separate decoder.

Non-goal for this phase:

- Full native LCD MS spectra decoding.
- Exact replacement of every LabSolutions TXT export section.
- Depending on adjacent `.txt` files at runtime.

## Phase 1: OLE Compound File Reader

Shimadzu `.lcd` files are OLE Compound Files. First implement read-only CFB/OLE stream listing and stream extraction.

Preferred approach:

- Implement a minimal internal CFB reader inside the existing named namespace hierarchy in `reader.cpp`, for example `mass_spec::reader::ole`.
- Keep it read-only.
- Support sector size, FAT, MiniFAT, directory entries, regular streams, and mini streams as needed by the fixtures.
- Do not introduce an external dependency unless the minimal reader becomes too large or fragile.

Fallback approach:

- Add a small source-only CFB/OLE reader under `src/core/external/cfb/` only if necessary.
- Vendor only the required read-only files.
- Avoid system dependencies.
- Keep Windows Rtools, Linux, and Docker builds reproducible.

Required helpers:

```cpp
namespace ole {
struct StreamInfo {
  std::string path;
  std::string normalized_path;
  std::uint64_t size = 0;
  bool is_mini_stream = false;
};

bool is_compound_file(const std::string& file_path);
std::vector<StreamInfo> list_streams(const std::string& file_path);
std::vector<std::uint8_t> read_stream(const std::string& file_path, const std::string& normalized_path);
}
```

Path normalization rules:

- Use `/` as separator.
- Remove leading `Root Entry/` if present.
- Trim empty path segments.
- Preserve original case for display, but use lowercase copies for matching.

Acceptance criteria:

- `inspect_lcd_streams.R` prints all streams for both LCD fixtures.
- It prints size, normalized path, and whether each stream is a candidate chromatogram stream.
- It does not crash on mini streams.

## Phase 2: Dynamic Candidate Discovery

Do not assume stream names are limited to `LC Raw Data/Chromatogram Ch1`.

Candidate discovery should scan all normalized stream paths and classify likely chromatogram streams.

Initial candidate patterns:

```text
LC Raw Data/Chromatogram Ch*
LC Raw Data/Status Trace*
LC Raw Data/*Chromatogram*
LC Raw Data/*Trace*
```

Discovery rules:

- Match case-insensitively.
- Exclude obvious method/config/report streams until proven to contain numeric chromatogram arrays.
- Store every candidate with original path, normalized path, basename, stream size, and parsed channel/trace number if present.
- Sort candidates by family, numeric channel/trace number, then normalized path.

Required helper:

```cpp
namespace shimadzu_lcd {
struct LcdStreamCandidate {
  std::string path;
  std::string normalized_path;
  std::string name;
  std::string family; // "Chromatogram", "Status Trace", "Unknown Trace"
  int channel_number = -1;
  std::uint64_t size = 0;
};

std::vector<LcdStreamCandidate> find_chromatogram_candidates(const std::vector<ole::StreamInfo>& streams);
}
```

Acceptance criteria:

- `260115_ADC.lcd` candidate count should be at least the detector chromatogram count and should be compared against the 8 TXT chromatogram-like traces.
- Candidate listing must make missing status traces obvious if they are stored elsewhere.
- `karl.lcd` candidates must be listed without assuming they are decodable.

## Phase 3: Stream Header Inspection

Before implementing decompression, inspect candidate stream bytes and infer stable headers.

Do not hard-code a single 24-byte layout until verified against the fixtures.

Implement header inspection utilities that print:

- stream size.
- first 64 bytes as hex.
- little-endian `uint16`, `uint32`, and `float` interpretations at common offsets.
- likely interval/count fields.
- whether payload length is consistent with candidate point counts from TXT.

Possible chromatogram header model, subject to fixture verification:

```cpp
struct LcdChromStreamHeader {
  std::uint32_t label = 0;
  std::uint32_t interval_ms = 0;
  std::uint32_t n_intervals = 0;
  std::uint32_t payload_size = 0;
  std::size_t payload_offset = 0;
};
```

Validation rules:

- `260115_ADC.txt` detector traces have 4201 points, 500 ms interval, 0 to 35 min.
- `260115_ADC.txt` status traces have 2101 points, 1000 ms interval, 0 to 35 min.
- Header parsing must support both if LCD stores both families similarly.

Acceptance criteria:

- `inspect_lcd_streams.R` prints candidate headers and inferred point counts.
- The plan for payload decoding is based on observed bytes, not assumption alone.

## Phase 4: Payload Decoder

Implement the Shimadzu chromatogram payload decoder only after stream/header inspection confirms where payload bytes begin.

Required function shape:

```cpp
namespace shimadzu_lcd {
std::vector<float> decode_chromatogram_payload(
  const std::vector<std::uint8_t>& stream,
  const LcdChromStreamHeader& header,
  std::size_t expected_points
);
}
```

Rules:

- Do not assume fixed-width `int16`, `int32`, `float`, or `double` until fixture bytes prove it.
- If using known Shimadzu delta-decompression logic from another implementation, verify its license before porting it.
- Add a short comment explaining the payload encoding after it is known.
- Fail with a stream-specific error when decoded point count differs from expected count.
- Return raw intensity first; apply scaling later through metadata.

Validation against `260115_ADC.txt`:

- Detector `Detector A-Ch1` raw values should match TXT raw values before multiplier.
- TXT currently returns scaled intensity because it applies `Intensity Multiplier = 0.001`.
- For comparison, divide TXT scaled intensity by `intensity_multiplier` or compare LCD scaled values after applying the same multiplier.

Known TXT reference for `Detector A-Ch1`:

```text
first raw values: -2, -2, -1, 2, 3, 3, 2, 1
time ~= 0.83333 min raw intensity ~= 12665
scaled intensity ~= 12.665 mV
```

Acceptance criteria:

- At least one detector chromatogram from `260115_ADC.lcd` decodes and matches the corresponding TXT trace over first values and selected peak region.
- Decoder errors include the stream path.

## Phase 8: Failure Behavior

Use clear errors:

Not an OLE file:

```text
File has .lcd extension but is not an OLE Compound File.
```

No candidate streams:

```text
Shimadzu LCD file detected, but no chromatogram or status trace streams were found.
```

Unsupported stream layout:

```text
Shimadzu LCD chromatogram stream was found, but the stream layout is not supported yet: <stream path>.
```

Decode failure:

```text
Shimadzu LCD chromatogram stream was found, but payload decoding failed for <stream path>: <reason>.
```

Metadata unavailable:

- Do not fail.
- Use empty strings or NaN defaults.

Exploration results:

- No tested simple decoder exactly matched the TXT trace or expected point count.
- Tested approaches included:
  - signed 8-bit direct and cumulative decoding.
  - little-endian and big-endian signed 16-bit direct and cumulative decoding.
  - signed-nibble cumulative decoding.
  - signed-nibble cumulative decoding with stride/phase reduction.
  - plain varint and zig-zag varint decoding.
  - `gzip` and `zlib` decompression attempts.
- The strongest partial signal is signed-nibble cumulative decoding:
  - Some offsets produce plausible small-intensity trace shapes.
  - Offset/phase variants can begin with values close to the TXT trace, including `-2, -2, -1, 2`.
  - The direct signed-nibble cumulative stream has about 20,950 decoded values, roughly 5 times the expected 4,201 points.
  - Fixed stride-5 sampling produces roughly 4,186 to 4,189 values depending on offset/phase, close but still not the expected 4,201 and not numerically correct.

Current inference:

- `RC` payload is likely a custom nibble/control-byte delta codec, not a simple fixed-width array or standard zlib/gzip stream.
- Values near the beginning suggest signed 4-bit delta nibbles are involved, but control bytes or periodic markers must be interpreted before point reconstruction.
- Stream bytes from offset 24 should be treated as an encoded command stream, not as a uniform numeric array.

Important `chromConverter` LCD codec documentation:

- 2D chromatogram streams are documented as `LSS Raw Data/Chromatogram Ch<#>`.
- The stream starts with the same 24-byte `RC` header we observed:
  - 4 bytes segment label `17234` (`RC`).
  - 4 bytes little-endian sampling rate in milliseconds.
  - 4 bytes little-endian number of values in the file.
  - 4 bytes little-endian total stream byte count.
  - 8 zero bytes.
- After the header, data are divided into subsegments.
- Each subsegment begins with a 2-byte byte count and ends with the same 2-byte byte count.
- Values are delta-encoded.
- The high nibble of each encoded value is a sign/length nibble:
  - high nibble gives the encoded width information.
  - even high nibbles are positive deltas.
  - odd high nibbles are negative deltas.
  - positive values are encoded as integers.
  - negative values are encoded as two's complement.
- `0x82` is skipped by their decoder.
- `0x00` decodes as a zero delta.
- The decoder resets the accumulator at each subsegment boundary.
