# streamfind Refactoring and Implementation Plan

## 1. Purpose

This document defines the implementation plan for refactoring the current **streamfind** repository into a modular, multi-interface platform centred on an almost standalone C++ library.

The target repository will contain:

```text
streamfind/
├── core/
├── python/
├── server/
├── frontend/
├── bindings/
└── integrations/
```

The central design principle is:

> `streamfind-core` is the authoritative implementation of project management, DuckDB persistence, analytical data processing, workflow execution, and native algorithms. All language bindings, servers, interfaces, and integrations consume this core rather than reimplementing its behaviour.

The refactoring must preserve existing streamfind functionality by first moving the complete, working R package—including its R, C++, Rcpp, native build, tests, and package assets—to `bindings/r`.  The R package is then refactored in place from `bindings/r` after the main standalone core has been completed under `core`, progressively removing the core's dependency on R, Rcpp, Shiny, and the R package build system.

# 2. Working Rules

## 2.1 General rules

- Implement the migration incrementally.
- Keep the complete R package functional from `bindings/r` until replacement
  interfaces reach feature parity.
- Do not perform a full rewrite of the existing C++ core.
- Reuse the current `src/core` implementation wherever technically appropriate.
- Complete the standalone core under `core` before refactoring the relocated R
  package.  Until then, change `bindings/r` only as needed to complete and
  validate the relocation.
- After the standalone core is complete, move Rcpp domain logic into the C++
  core when it represents domain logic rather than language conversion.
- Do not duplicate project, workflow, storage, or algorithm logic in Python, FastAPI, React, R, or Cogniflow integrations.
- Treat `streamfind-core` as the source of truth for project state and processing behaviour.
- Use `Method` for the public, documented, workflow-executed processing unit.
  `Algorithm` refers only to an internal implementation helper and must not
  create a second public registry, metadata model, or interface contract.
- A project owns one versioned workflow.  The core has no `Run` aggregate;
  server-side jobs are transport state, while execution provenance belongs to
  the project audit/results infrastructure.
- Preserve the current C++ table-creation mechanism during extraction.  New
  formal migration infrastructure is a later, evidence-based decision rather
  than a prerequisite for the refactor.
- Keep transport, serialization, user-interface, and language-specific concerns outside the core.
- Add tests before or alongside each major migration.
- Preserve current DuckDB schemas unless a phase explicitly introduces a versioned migration.
- Do not add legacy compatibility logic unless explicitly required by a migration phase.
- Do not manually edit autogenerated binding files.
- Keep generated files out of source-controlled implementation directories unless they are required distribution artefacts.
- Establish the target repository layout in the first implementation phase.  Move
  complete package/integration boundaries as atomic relocations, then migrate
  their implementation by subsystem from their new homes.
- Treat the Phase 1 R-package move as a preservation move: move all R, C++,
  Rcpp, build, test, documentation, and package assets together; do not delete,
  rewrite, or split them as part of that move.
- Prefer explicit interfaces and typed data structures over generic unstructured maps.
- Use consistent naming across C++, Python, REST endpoints, and integrations.
- Document every public API.
- Fail with structured errors rather than silent fallback behaviour.

## 2.2 Native build rules

- Use CMake as the authoritative native build system.
- Use C++20 unless an external dependency requires C++17.
- The core must build without R, Rcpp, Python, pybind11, FastAPI, Node.js, or React.
- External libraries must be linked through explicit CMake targets.
- Runtime libraries must be installed through CMake install rules.
- Do not rely on environment-specific absolute paths.
- Do not use R `Makevars` as the authoritative native build definition after migration.
- Support out-of-source builds.
- Add CMake presets for supported development and CI environments.
- Keep public headers separate from private implementation headers.
- Use symbol export macros for Windows shared-library builds.
- Hide non-public symbols where supported.
- Define and test static and shared builds where practical.
- Do not expose third-party implementation types in the public core API.

## 2.3 Python rules

- Use `pybind11` only for binding the native core.
- Use `scikit-build-core` as the Python build backend.
- Use CMake to compile the native extension.
- Keep `_core` private to the Python package.
- Public Python code must depend on the Python application API, not directly on `_core`.
- Prefer Python-friendly wrappers over one-to-one exposure of every C++ class.
- Release the Python GIL for long-running native operations.
- Reacquire the GIL only for Python callbacks or object creation.
- Do not implement analytical algorithms in Python when they belong in the C++ core.
- Do not use Python as a substitute for missing core functionality.
- Package native runtime dependencies inside wheels where licensing permits.
- Build binary wheels for supported platforms.
- Source builds may require a compiler; normal end-user installation must not.

## 2.4 Server rules

- Use FastAPI as the application server.
- Use Pydantic models for API input and output validation.
- FastAPI routes must call a service layer, not pybind11 bindings directly.
- Long-running workflows must execute outside request handlers.
- Use a job abstraction for queued, running, completed, failed, and cancelled tasks.
- Persist server job state and project execution provenance.
- Support progress events through WebSocket or Server-Sent Events.
- Do not send large chromatograms, spectra, or feature matrices as unbounded JSON.
- Use Arrow, Parquet, files, streaming, or paginated/downsampled responses for large data.
- Keep local single-user and remote multi-user deployment concerns separable.

## 2.5 Frontend rules

- Use React and TypeScript.
- Do not embed analytical or project logic in React.
- Generate or derive API clients from the FastAPI OpenAPI specification where practical.
- Keep server state and UI state separate.
- Support long-running job status, cancellation, failure details, and progress.
- Treat the FastAPI API as the only backend contract.
- Do not call the C++ library, Python extension, or DuckDB directly from the frontend.
- Preserve accessibility and keyboard operation.
- Design large-table and plotting components for analytical-scale data.

## 2.6 R binding rules

- `bindings/r` is the only home of the streamfind R package from Phase 1 onward.
- Move the complete R package boundary there in one commit: package metadata,
  R sources, native R sources, installed assets, tests, vignettes, Rd/roxygen
  inputs, package build files, and R-package-specific documentation/configuration.
- Include every C++ and Rcpp source and its native build configuration in that
  move; `bindings/r` remains a complete, working package after relocation.
- Update all package-relative paths, CI jobs, Docker/build scripts, pkgdown and
  development commands to run with `bindings/r` as the package root.  Do not
  leave a second buildable package at the repository root.
- Keep the R package installable and testable from `bindings/r` during migration.
- During Phase 1, make only path, packaging, and build-command repairs needed
  to run it from `bindings/r`; do not begin R-layer refactoring or remove
  implementation from the package.
- Begin refactoring the R package in place only after the main standalone core
  under `core` is complete and can provide the required replacement behaviour.
- Move only R-specific conversion and ergonomics into the R binding layer.
- Keep domain logic in `streamfind-core`.
- Use Rcpp as a native binding where it remains justified.
- `reticulate` may be used for transitional or high-level integration, but must not become a second implementation of core behaviour.
- Do not require users to compile the core when prebuilt R binaries are available.

## 2.7 Integration rules

- `integrations/cf-streamfind` is the only home of the Cogniflow integration;
  the existing `python/cf_streamfind` tree is moved there in Phase 1.
- `cf-streamfind` must consume the public Python API.
- Cogniflow-specific context, contracts, package registration, and dispatch remain in `integrations/cf-streamfind`.
- Do not couple `streamfind-core` to Cogniflow.
- Do not make FastAPI mandatory for in-process Cogniflow use.
- Integrations must translate external contracts into streamfind service calls.
- Integrations must not access private `_core` symbols.
- `cf-streamfind` must project and validate the public operation catalogue as
  TriG; it must not make the core depend on Stonecastle or RDF tooling.
- Cogniflow semantic operation IRIs must be the same canonical IRIs used by the
  core registry and persisted workflows.
- `cf-streamfind` must depend on the installed public `streamfind` Python
  package.  After its in-place refactoring, it must not compile C++ steps,
  include core headers, link DuckDB/OpenBabel, or bundle a second native runtime.

# 5. Component Responsibilities

## 5.1 `core`

`core` is the authoritative native implementation.

It must manage:

- project creation and opening;
- project identifiers and metadata;
- DuckDB connection lifecycle;
- schema creation and validation;
- transactions;
- analysis import;
- file-reader dispatch;
- chromatogram and spectrum persistence;
- the project workflow definition;
- method registration;
- workflow validation;
- workflow execution;
- native method execution;
- cache-key generation, cache reuse, and cache clearing;
- result persistence;
- structured logging events;
- cancellation checks;
- progress events;
- native error types;
- version and capability discovery.

It must not contain:

- Rcpp types;
- `SEXP`;
- Python objects;
- pybind11 code;
- FastAPI concepts;
- HTTP;
- React concepts;
- Cogniflow contracts;
- GUI state;
- language-specific exceptions;
- direct user-interface formatting.

## 5.2 `python`

The Python package provides:

- Pythonic project classes;
- workflow and method models;
- typed parameters;
- exception mapping;
- resource lifecycle management;
- context managers;
- progress callback adapters;
- NumPy and Arrow conversion;
- CLI commands where appropriate;
- stable public APIs for FastAPI and Cogniflow.
- the canonical operation invocation service, operation request/result models,
  runtime configuration, and capability/catalogue access shared by every
  non-R interface.

It must not become the authoritative location of:

- schema definitions already owned by the core;
- native method implementations;
- workflow execution semantics;
- DuckDB transaction logic;
- file parsing;
- project validation logic.

## 5.3 `server`

The server provides:

- REST endpoints;
- WebSocket or SSE job events;
- request validation;
- job submission;
- job isolation;
- process lifecycle;
- authentication hooks;
- upload/download handling;
- result pagination;
- binary data transfer;
- deployment configuration;
- OpenAPI generation.

The server must call the public Python API.

## 5.4 `frontend`

The frontend provides:

- project selection and creation;
- file import;
- analysis browsing;
- chromatogram and spectrum visualization;
- workflow creation and editing;
- method parameter forms;
- workflow execution submission;
- execution progress;
- result exploration;
- report access;
- error presentation.

It must not access DuckDB directly.

## 5.5 `bindings`

`bindings/r` provides the R interface.

The initial goal is not to remove R functionality but to make R a consumer of the core.

The binding layer may provide:

- R6 or S7 wrappers;
- R data-frame conversion;
- R plotting helpers;
- compatibility with existing APIs;
- Quarto and R Markdown support;
- optional `reticulate` integration.

## 5.6 `integrations`

`integrations/cf-streamfind` provides the Cogniflow adapter.

It is responsible for:

- operation registration;
- Cogniflow contract mapping;
- context translation;
- streamfind call orchestration;
- result translation;
- package metadata;
- integration-specific tests.

It must remain a thin distribution boundary: Cogniflow package registration,
TriG semantics, execution-context conversion, progress/error translation, and
dispatch to the public Python operation service.  It must not contain a second
native extension, algorithm wrappers, project classes, parameter validators, or
runtime-library discovery implementation.

## 5.7 Project profiles, capabilities, and applications

Use a composed project model, not a deep hierarchy of persistent project
classes.  `Project` is the single generic aggregate responsible for identity,
storage lifecycle, common workflow/execution behaviour, and the installed capability
set.  A project profile is a creation-time template; a capability is a
versioned domain module that can contribute schema migrations, readers,
operations, result types, query services, and its own DuckDB tables.

```text
Project
├── generic capabilities: project, analyses, workflow, results, cache
├── mass_spec capability
│   ├── chromatograms capability
│   └── spectra capability
└── nta capability (requires mass_spec)

Frontend applications/workspaces
├── MassSpec Explorer        requires mass_spec
├── Chromatogram Workbench   requires chromatograms
├── Spectra Workbench        requires spectra
└── NTA Workbench            requires mass_spec + nta
```

For example, a MassSpec profile may enable the `mass_spec` capability and its
reader support; chromatograms, spectra, and NTA are separately versioned
capabilities with explicit dependencies.  A project can therefore contain both
spectra and chromatograms, and later gain NTA, without changing its persisted
class or requiring a `ProjectMassSpecSpectra`,
`ProjectMassSpecChromatograms`, or `ProjectMassSpecNonTargetAnalysis` subtype.

`ProjectMassSpec*` may remain as R compatibility wrappers while the R package
is being refactored, but they must delegate to the generic core `Project` and
capability services.  They are not core types, database discriminators, or
server-routing types.

Applications are frontend/server application-service compositions, not data
models.  They define navigation, views, default workflows, and authorization
requirements for a set of capabilities; they never own a separate copy of
project data or algorithms.

The generic project schema contains only shared tables such as project
metadata, analyses, one project workflow, results, cache, audit history, and capability
state.  Each enabled domain capability creates and owns its additional tables.
For the initial migration, the current table-creation SQL and table semantics
in the existing `src/core` C++ implementation are the behavioural baseline:
move them into the matching domain implementation under `core/src` (for
example, `core/src/mass_spec` or `core/src/nta`) rather than
folding them into the generic project schema or recreating them in an interface.

After that preservation move, table ownership is append-only.  A domain
capability may create only new tables that it owns; it must not add, remove,
rename, or alter columns, constraints, indexes, or table definitions owned by
the generic `Project` layer or by a preceding domain capability.  For example,
MassSpec must not modify generic project tables, and NTA must not modify either
generic project or MassSpec tables.  A new relationship or attribute is stored
in a new capability-owned extension table keyed to the earlier table's stable
primary key.

# 6. Core Architectural Boundaries

## 6.1 Core public API layers

Use three internal layers:

```text
Public API
    │
Application services
    │
Domain and infrastructure
```

### Public API

Stable types intended for consumers:

- `Project`
- `ProjectOptions`
- `ProjectInfo`
- `ProjectDescriptor`
- `ProjectProfile`
- `CapabilityDescriptor`
- `Analysis`
- `Workflow`
- `MethodDefinition`
- `ExecutionStatus`
- `ResultSet`
- `ProgressEvent`
- `streamfind_error`

### Application services

Coordinate use cases:

- `ProjectService`
- `AnalysisService`
- `WorkflowService`
- `ExecutionService`
- `ResultService`
- `SchemaService`

### Domain and infrastructure

Implementation details:

- DuckDB repositories;
- file readers;
- algorithm registries;
- workflow planner;
- execution context;
- transaction manager;
- result writers;
- logging sinks.

Consumers should not access repository implementation classes directly.

## 6.2 Proposed C++ API direction

```cpp
namespace streamfind {

struct ProjectOptions {
    std::filesystem::path database_path;
    std::string project_id;
    std::optional<std::string> profile_id;
    std::vector<CapabilityRequirement> initial_capabilities;
    bool create_if_missing{false};
};

class Project {
public:
    static Project open(const ProjectOptions& options);
    static Project create(const ProjectOptions& options);

    const ProjectInfo& info() const;
    ProjectDescriptor describe() const;
    std::vector<CapabilityDescriptor> capabilities() const;
    void enable_capability(const CapabilityRequirement& requirement);

    AnalysisImportResult add_analyses(
        const std::vector<std::filesystem::path>& files,
        const AnalysisImportOptions& options = {}
    );

    Workflow workflow() const;
    void update_workflow(const WorkflowDefinition& definition);

    ExecutionStatus execute(
        const ExecutionOptions& options = {}
    );

    ResultSet results() const;

    void close();
};

}
```

The public C++ API should use:

- `std::filesystem::path`;
- `std::string`;
- `std::vector`;
- `std::optional`;
- `std::chrono`;
- stable streamfind value types;
- RAII for native resources.

Avoid exposing:

- raw DuckDB handles;
- Rcpp data structures;
- pybind11 types;
- external-library classes;
- raw ownership pointers.

# 7. DuckDB Ownership and Persistence

## 7.1 Core responsibility

The core owns all DuckDB interaction.

Language bindings must request operations through the core rather than issue SQL against streamfind project databases.

## 7.2 Required storage modules

```text
core/src/storage/
├── connection.cpp
├── transaction.cpp
├── schema.cpp
├── migrations.cpp
├── project_repository.cpp
├── analysis_repository.cpp
├── workflow_repository.cpp
├── cache_repository.cpp
├── audit_repository.cpp
└── result_repository.cpp
```

The initial extraction keeps the existing C++ table-creation approach and
source ownership intact.  Move the current files into the standalone core with
their table-creation functions unchanged where practical:

```text
core/src/project/project.cpp       # PROJECT, CACHE, AUDIT_TRAIL
core/src/mass_spec/mass_spec.cpp   # MS_ANALYSES and headers
core/src/mass_spec/processing.cpp  # MS_CHROMATOGRAMS
core/src/nta/nta.cpp               # NTA domain tables
```

Do not introduce a separate per-migration file hierarchy, a new
`schema_migrations` table, or an `owner_scope` field merely because of the
refactoring.  These are possible future mechanisms only if real project
upgrade requirements cannot be handled by the current C++ schema code.

## 7.3 Database rules

- One project database may contain one or more logical project records only if explicitly supported.
- Project opening must validate schema version.
- Every schema change must be implemented and tested through the C++ schema
  code.  It requires a formal migration only after migration tracking is
  intentionally introduced.
- Where formal migrations are later required, they must be ordered,
  transactional, and testable.
- Store framework version and schema version separately.
- Store enabled capability identifiers and versions in the generic project
  schema, and validate their dependency graph when opening a project.
- Keep each capability's existing table-creation SQL with its C++ domain
  implementation.  No R, Python, server, frontend, or Cogniflow component may
  create or alter domain tables.
- Preserve and relocate the existing domain-table behaviour from `src/core`
  before redesigning it.  After the extraction, schema evolution is append-only:
  add new owner-scoped tables rather than alter existing tables.
- A domain capability must not execute `ALTER TABLE`, `DROP TABLE`, `RENAME`,
  or equivalent DDL against a table owned by the generic project layer or a
  preceding capability.  Enforce this with table-ownership and schema tests.
- Methods and their internal algorithms must not issue ad hoc SQL from
  unrelated modules.
- Repository classes own SQL.
- Use prepared statements for dynamic parameters.
- Use transactions for multi-table operations.
- Add integrity checks for analysis, workflow, execution-provenance, and result references.
- Define concurrency behaviour explicitly.
- Prevent simultaneous unsafe writers.
- Support read-only project opening where appropriate.

## 7.4 Future schema-evolution model

The initial refactoring does not replace the current C++ `CREATE TABLE IF NOT
EXISTS` and targeted `ALTER TABLE` approach.  Once the current schema has been
preserved in the standalone core, future changes are append-only and must add
new owned tables rather than alter existing ones.  Introduce formal migration
tracking only when a released-project upgrade cannot be safely handled by that
existing mechanism, and retain the same C++ ownership and call path.

Do not predefine a migration table or file layout now.  If a concrete future
upgrade requires formal tracking, design the smallest compatible extension of
the existing C++ mechanism at that time, with upgrade tests for the affected
released schemas.

# 8. Methods and Data Processing

## 8.1 Internal algorithm contract

Algorithms may implement a common native interface behind a public `Method`.

```cpp
class Algorithm {
public:
    virtual ~Algorithm() = default;

    virtual MethodResult execute(
        ExecutionContext& context,
        const ParameterSet& parameters
    ) = 0;
};
```

## 8.2 Method registry

The core should provide a registry:

```cpp
registry.register_method(
    "streamfind.mass_spec.detect_features",
    []() { return std::make_unique<DetectFeatures>(); }
);
```

Each method must define:

- stable operation identifier;
- display name;
- version;
- input types;
- output types;
- parameter schema;
- validation rules;
- execution function;
- progress reporting;
- cancellation checkpoints.

## 8.3 Data access rules

Algorithms receive access through an `ExecutionContext`.

The context may provide:

- project metadata;
- transaction;
- repositories;
- temporary storage;
- progress reporter;
- cancellation token;
- logging interface;
- execution options.

Algorithms must not:

- create independent unmanaged DuckDB connections;
- depend on R;
- depend on Python;
- write arbitrary output tables without registration;
- silently change schemas.

## 8.4 Native method model

The current R `Method` metadata object becomes a public native C++ `Method`
contract.  It is the unit that a workflow contains and executes; an
`Algorithm` is an internal implementation detail that a method may use.  The
`Method` contract itself exposes its complete `MethodDefinition` metadata, so
the same native object supports execution, validation, usage, and generated
documentation.

`MethodDefinition` must preserve the useful current R metadata: method name,
required preceding methods, owning domain capability, maximum permitted
occurrences in the single workflow, developer/contact, reference link/DOI, and
typed/default parameter values.  It also includes the canonical operation IRI,
input/output contract, validation rules, cache policy, and implementation
version.

This metadata is the single public source for method usage: required preceding
methods, parameter names/defaults/constraints/units, accepted inputs, produced
outputs, cache behaviour, developer and scientific references, and examples.
The CLI, FastAPI/OpenAPI schemas, React parameter forms, R wrappers/reference
pages, Cogniflow TriG projection, and documentation generator must consume it
through the public C++/Python catalogue API rather than maintaining parallel
method documentation.

The core owns the base `Method` interface and method registry.  Each domain
defines its concrete methods in C++—for example MassSpec import/processing
methods in `core/src/mass_spec` and NTA methods in `core/src/nta`—and registers
them with their capability.  The R `Method` class becomes a compatibility
wrapper over the exported C++ metadata; it must not remain the authoritative
method definition or validator.

## 8.5 Cache reuse between methods

Preserve the existing generic C++ `CACHE` table and wrapper in
`project/project.cpp` as shared project infrastructure.  The workflow executor
consults it before executing a cacheable method and stores a reusable result
after successful execution.  Cache access occurs only through the native
`ExecutionContext`; R, Python, FastAPI, React, and Cogniflow do not construct
or query cache rows directly.

A cache key must be deterministic and include the method's canonical operation
IRI and implementation/descriptor version, canonical resolved parameters,
input artefact identities or content hashes, relevant project/capability
versions, and any declared execution options that affect output.  Therefore a
method reuses a result only when every declared input is equivalent.  A changed
input, parameter, method version, or relevant capability version produces a
new key rather than risking stale output.

Each native method declares whether it is cacheable and supplies a stable
result serializer/validator.  Cache hits, misses, writes, and explicit clears
are recorded in the existing project audit trail.  The project may explicitly
clear its cache, but cache invalidation is normally achieved by the key rather
than by an interface-specific rule.

## 8.6 Operation catalogue, validation, and reference documentation

`MethodDefinition` is the authoritative, executable description of every
public method.  It must be complete enough for the core to validate a
workflow before execution and for every interface to render the same reference
documentation.  Doxygen documents the C++ developer API; it is not the source
of truth for an operation's user-facing contract.

Each registered operation must provide a versioned descriptor containing:

- a canonical operation IRI, for example
  `urn:streamfind:operation:mass_spec:detect_features`, used in persisted
  workflows and semantic integrations;
- a lower-case display slug and title, summary, full description, category,
  status, version, change notes, and citations/provenance;
- project compatibility and required capabilities;
- named input, output, and parameter ports, including descriptions, semantic
  types, cardinality, nullability, units, default values, enumerations, bounds,
  regular expressions, and cross-field validation rules;
- result artefacts, persisted tables/files, side effects, determinism,
  resource expectations, and cancellation/progress behaviour; and
- implementation version and a descriptor fingerprint recorded with each execution.

The core must expose this catalogue through its public API, including
`describe_operation`, `list_operations`, catalogue schema version, and
fingerprint.  The CLI must export it as a versioned machine-readable document;
the Python, R, and server layers consume that export or the equivalent public
API rather than maintaining independent parameter lists.

Generate human reference pages from the catalogue for the main documentation
site, CLI help, OpenAPI/Pydantic schemas, and R reference material.  Preserve
the existing roxygen documentation during the relocation; after the core is
complete, replace duplicated method parameter and input/output text with
generated R sources or generated roxygen fragments keyed by the canonical
operation IRI.  Keep hand-written R guides, tutorials, and scientific context
next to the generated reference rather than trying to generate narrative
documentation from metadata.

The catalogue is part of the executable contract: tests must verify that every
registered implementation has one valid descriptor, that its parameter
validator accepts exactly the documented contract, and that descriptor changes
require an intentional version/change-note update.

## 8.7 Cogniflow semantic projection

The core must not depend on RDF, TriG, SHACL, or Stonecastle at runtime.
Instead, `cf-streamfind` projects the exported core catalogue into the
Stonecastle semantic model and validates the projection during its build and
tests.  The core catalogue owns execution semantics; the Cogniflow extension
owns Cogniflow-specific semantic enrichment.  Neither may redefine the other
layer's responsibility.

For each core operation, the projection produces one resource that is both a
Stonecastle service operation and a Cogniflow processing step, with the same
canonical operation IRI.  Its TriG declares the executable service binding,
input and output SHACL shapes, and processing ports:

```trig
sfop:detect_features
    a sc:ServiceOperation, cfproc:ProcessingStep ;
    sc:operationIri "urn:streamfind:operation:mass_spec:detect_features" ;
    sc:pythonCallable "cf_streamfind.services:detect_features" ;
    sc:inputShape sfshape:DetectFeaturesInput ;
    sc:outputShape sfshape:DetectFeaturesOutput ;
    cfproc:hasPort sfop:analyses, sfop:parameters, sfop:features .
```

The generated shapes and ports mirror the core descriptor's input, output, and
parameter rules.  Hand-authored enrichment may add domain ontology mappings,
controlled vocabularies, provenance terms, pipeline examples, and user-facing
labels; it must identify the same IRI and must not alter executable validation
rules.  CI validates the TriG with Stonecastle/SHACL tooling, verifies a
one-to-one operation mapping, and fails if the core catalogue fingerprint and
generated projection differ.

## 15.4 Stonecastle TriG extension

`integrations/cf-streamfind` is a Cogniflow extension package, not a second
streamfind implementation.  Its semantic package should follow Stonecastle's
package/service/shape/processing-step split:

```text
integrations/cf-streamfind/
├── src/cf_streamfind/
│   ├── services.py                 # thin public-Python-API adapters
│   ├── semantics/
│   │   ├── package.trig            # package identity and semantic ownership
│   │   ├── services.trig           # generated service-operation bindings
│   │   ├── shapes.trig             # generated SHACL input/output shapes
│   │   ├── steps.trig              # generated cfproc processing ports
│   │   └── enrichment.trig         # reviewed domain/provenance mappings
│   └── generated/
│       └── operation_catalog.trig  # build artifact; not hand edited
├── tools/
│   └── project_operation_catalog.py
└── tests/
    ├── test_semantic_projection.py
    └── test_operation_dispatch.py
```

The projection tool reads only the installed or built public streamfind
catalogue, emits deterministic TriG, and records the catalogue version and
fingerprint.  The package build includes the generated semantic resources and
registers them with the Stonecastle semantic manifest/index.  Source-controlled
TriG contains only the package declaration and reviewed enrichment that cannot
be inferred from the core contract.  The generated catalogue is a distribution
artifact, never a manually edited alternative operation definition.

At runtime, `cf-streamfind` resolves the semantic operation IRI, verifies that
it exists in the installed core catalogue at the declared compatible version,
converts the validated Cogniflow value to the public Python model, and invokes
the matching public service.  It returns only the documented outputs and maps
core progress/errors to Cogniflow equivalents.  It must reject a stale or
incompatible semantic projection rather than silently guessing a parameter
mapping.

## 15.5 Package anti-duplication contract

Keep two installable packages because their distribution and runtime consumers
are different, but give them one execution implementation:

```text
streamfind Python package
    owns: public project/capability models, operation catalogue,
          OperationService, validation, native runtime configuration,
          core binding, CLI-facing services
    consumed by: FastAPI server, CLI, cf-streamfind

cf-streamfind package
    owns: Cogniflow entry point, TriG projection/enrichment,
          Cogniflow-value <-> public-operation-request conversion,
          Cogniflow progress/error translation
    depends on: streamfind Python package
```

`cf-streamfind` uses one generic semantic dispatcher that receives the
canonical operation IRI and calls `OperationService.execute`.  Do not maintain
one hand-written Python or C++ wrapper for every streamfind operation.  If a
Cogniflow runtime requires a distinct callable per semantic operation, generate
thin Python dispatch functions from the public catalogue; their only action is
to forward the operation IRI and converted request to the generic dispatcher.

Move the existing DuckDB/OpenBabel discovery and bundled-runtime setup into the
core/Python package distribution.  `cf-streamfind` calls the public runtime
configuration API and declares a compatible `streamfind` dependency; it does
not package the same libraries, CMake build, or native step extension again.
Keep algorithm and parameter-validation tests in `streamfind`; keep only
semantic-projection, conversion, package-discovery, and end-to-end dispatch
tests in `cf-streamfind`.

## Authoritative implementation sequence

### Foundation 0 — Baseline, contracts, and move manifest

Complete the Phase 0 inventory, then create a relocation manifest with each
current source path, its destination, test command, owner, and any changed
relative paths.  Capture golden DuckDB databases and representative outputs for
the base project, MassSpec, and NTA workflows.  This is the only discovery
gate; it must not postpone the structural move.

**Exit criteria:** every root-level R-package path and every
`python/cf_streamfind` path has one target path, and the baseline commands are
recorded.

### Foundation 1 — Implement the target repository layout

Implement the complete structure in Section 4.  Relocate the R package to
`bindings/r` and Cogniflow integration to `integrations/cf-streamfind` as real
filesystem moves.  Add root build entry points that delegate to those new
directories, and repair package-relative paths, CI, Docker, and documentation.
Do not retain root-level forwarding packages or a `python/cf_streamfind`
compatibility copy.

**Exit criteria:** the R package builds, checks, and tests from `bindings/r`;
the integration imports and tests from `integrations/cf-streamfind`; root build
and developer commands invoke those paths; and the source tree contains only
one copy of each package.

### Platform 2A — Native base project and DuckDB kernel

Create the standalone CMake core and migrate the smallest shared vertical
slice: error model, logging, configuration, project identity and metadata,
create/open/close, DuckDB connection lifecycle, transactions, schema
creation/validation, and the existing C++ table-creation/targeted-alter
behaviour.  Establish the public C++
project API and the storage boundary before any MassSpec or NTA types are
introduced.  Migrate SQL currently embedded in Rcpp into this layer.

**Exit criteria:** a C++ test creates, reopens, validates, migrates, and
transacts against a project database without R, Python, or domain modules.

### Platform 2B — Shared execution, result, and extension contracts

Add the shared contracts on which every domain project depends: analysis
metadata, file-reader registration, operation identifiers, typed parameters,
the single project workflow and validation, method registry, cache reuse,
execution provenance, structured results, cancellation, and progress events.  Keep the concrete
domain algorithms out of this sub-phase.  Define the complete executable
operation catalogue and its versioned export in this sub-phase.  Rcpp contains only conversion,
external pointer lifecycle, callbacks, and exception mapping.

**Exit criteria:** native tests can register a test method, validate and execute
the project workflow, persist a result/cache entry and audit provenance, and observe cancellation/progress using only
the generic project API.  The same test operation has an exported, complete
descriptor with a canonical operation IRI.

### Platform 2C — Public API, CLI, and service/API baseline

Build the public Python package around stable, coarse-grained core services;
add the `streamfind` CLI for project create/open/inspect, schema status,
workflow validation/execution, execution status, cache inspection, and result export.  In parallel,
create the FastAPI service boundary with health, project, workflow, job, and
result endpoints backed by the same Python service layer.  This is an API and
CLI foundation, not a domain UI: it must expose generic projects and the test
operation from Platform 2B before MassSpec functionality is added.

**Exit criteria:** a binary-wheel install supports the base project API and
CLI without R; API contract tests exercise the same operations through FastAPI;
neither the CLI nor the server accesses DuckDB or `_core` directly.

### Domain 3 — MassSpec project

Migrate the MassSpec-specific project model, reader dispatch and formats,
chromatogram/spectrum persistence, query APIs, and one complete MassSpec
workflow into `core/mass_spec` as versioned MassSpec, chromatogram, and spectra
capabilities rather than project subclasses.  Bind the resulting public
operations through Python, CLI, FastAPI, the matching frontend plugins, and the
R wrapper in `bindings/r`.  Use database and result comparisons against the
Phase 0 fixtures.

**Exit criteria:** the first vertical slice in Section 22 works end to end
through C++, R, Python/CLI, and FastAPI, with no MassSpec SQL or domain logic
remaining in Rcpp or interfaces.

### Domain 4 — NTA project

Migrate the NTA project model and methods in dependency order: feature loading,
feature finding/grouping/filling, blank and quality filtering, components,
annotation, suspect/transformation-product workflows, and external-tool
adapters.  Define NTA as a capability that explicitly requires MassSpec.  Each
operation is registered through the shared workflow contract and made available
consistently in R, Python/CLI, FastAPI, and the NTA frontend plugin.

**Exit criteria:** representative NTA workflows reproduce approved baseline
outputs and all new operations have native, binding, and regression coverage.

### Domain 5+ — Remaining project families and optional capabilities

Migrate additional project types, readers, algorithms, reports, and specialist
tools one coherent feature family at a time.  Each family follows the same
order: native implementation and schema migration; public API; CLI/API;
R-binding compatibility; integration and regression tests.  A family may not
bypass the shared project, storage, workflow, cache, execution, or result contracts.

### Delivery 6 — Interfaces, integrations, and frontend parity

Refactor `integrations/cf-streamfind` in place to call only the public Python
API, mapping Cogniflow contracts, progress, errors, and operation identifiers.
Generate and validate its Stonecastle TriG projection from the public core
catalogue, then add reviewed semantic enrichment without duplicating operation
contracts.
Complete server jobs/events and then build the React features for capabilities
that have reached API parity.  Freeze and ultimately retire Shiny only after
the supported workflow matrix has React/FastAPI equivalents.

**Exit criteria:** Cogniflow imports no `_core` and accesses no DuckDB; long
workflow jobs execute outside HTTP handlers; the semantic projection passes SHACL and
catalogue-fingerprint validation; all supported UI workflows have documented
parity or an explicit legacy status.

### Delivery 7 — Distribution and release hardening

Finalize R binary packaging from `bindings/r`, Python wheel repair, CMake
install/export rules, schema upgrade testing, concurrency/failure testing,
performance baselines, licence/runtime audits, and release automation.

**Exit criteria:** clean-system installations exercise R, Python/CLI, server,
and integration entry points against migrated projects, with documented support
and upgrade policies.

# 21. Recommended Implementation Order Within `core`

Migrate in this sequence:

1. errors and logging;
2. DuckDB connection and transaction management;
3. current schema creation, validation, and targeted C++ upgrades;
4. project identity, metadata, and create/open/close;
5. generic result and query contracts;
6. workflow definitions, operation identifiers, and parameter schemas;
7. method registry, cache reuse, execution provenance, progress, and cancellation;
8. public C++ service API stabilization;
9. MassSpec analysis metadata, reader interfaces, and chromatogram/spectrum
   persistence;
10. one complete MassSpec processing workflow and result query API;
11. remaining MassSpec algorithms;
12. NTA project model and feature data;
13. NTA algorithms in workflow dependency order;
14. remaining project families and optional capabilities.

Expose the generic project services through Python, CLI, and FastAPI after item
8.  Bind each domain family only after its core slice is stable; this prevents
both R and Python from becoming temporary owners of domain behaviour.

# 24. Risks and Mitigations

## Risk: hidden domain logic in R

Mitigation:

- complete Phase 0 inventory;
- add regression tests;
- migrate by use case;
- compare database outputs.

## Risk: unstable C++ API

Mitigation:

- keep internal implementation private;
- expose coarse-grained services;
- do not bind internal repository classes;
- version public contracts.

## Risk: native dependency packaging

Mitigation:

- define explicit dependency policy;
- use CI wheel validation;
- test on clean machines;
- audit DLL and shared-library loading.

## Risk: multi-process DuckDB access

Mitigation:

- document writer ownership;
- serialize project writes;
- use process-safe job coordination;
- add lock and failure tests.

## Risk: large analytical data through REST

Mitigation:

- binary formats;
- pagination;
- server-side downsampling;
- download endpoints.

## Risk: simultaneous R, Python, and server maintenance

Mitigation:

- one core implementation;
- shared operation identifiers;
- shared schemas;
- generated clients;
- staged deprecation.

## Risk: long migration period

Mitigation:

- vertical slices;
- keep current releases working;
- phase-gated acceptance criteria;
- avoid broad rewrites.

# 26. Final Target State

The final system should operate as follows:

```text
streamfind-core
    owns:
        projects
        DuckDB
        schemas
        readers
        workflow
        methods
        cache
        execution provenance
        results

streamfind Python
    owns:
        Python API
        object ergonomics
        type conversion
        Python services

streamfind-server
    owns:
        HTTP
        WebSocket/SSE
        jobs
        uploads
        downloads
        deployment configuration

streamfind frontend
    owns:
        user interface
        plotting
        workflow editing
        processing-job monitoring

bindings/r
    owns:
        R API
        R conversion
        compatibility
        reporting integration

integrations/cf-streamfind
    owns:
        Cogniflow mapping
        contracts
        integration behaviour
```

The key constraint throughout implementation is:

> Every endpoint must depend on the same streamfind core behaviour. No interface may become an independent implementation of project management, storage, workflow execution, or analytical processing.
